# 0009 — Gmail API over HTTPS as the production mail transport

- Status: Accepted
- Date: 2026-07-19
- Deciders: Developer (senior full-stack), per owner's decision (no third-party ESP)
- Related: `apps/api/src/mail/mail.service.ts`, `apps/api/src/mail/gmail-api.transport.ts`,
  `ops/scripts/gmail-oauth-setup.mjs`

## Context

Outbound email (verification, password reset, project invitations) worked locally
via SMTP (`smtp.gmail.com:465`, App Password) but **failed silently in production on
Railway's trial tier**. Railway trial blackholes all outbound SMTP: connection
packets are dropped with no RST, so every connect attempt hangs until it hits the
transporter's bounded timeouts (`connectionTimeout` 5s, `socketTimeout` 15s) and the
send fails. This is a platform-level network egress policy, not a code bug — no SMTP
host/port/credential change can fix it, because the SMTP ports themselves are
unreachable from the trial runtime.

HTTPS egress (443), by contrast, is never blocked — the API already makes outbound
HTTPS calls (Supabase, Google OAuth). So the delivery **channel** must change from
SMTP to HTTPS while keeping the **sender identity** (the owner's Gmail account) so
that DMARC still aligns.

The owner explicitly does not want a third-party Email Service Provider (SendGrid,
Postmark, Resend, etc.) — mail should stay self-owned on the existing Gmail account.

## Decision

Add a **Gmail API (HTTPS) transport** and make it the primary delivery path when
configured; keep the existing SMTP transporter as the local-dev / fallback path.

1. **New transport** `apps/api/src/mail/gmail-api.transport.ts`:
   - OAuth2 **refresh-token grant** against `https://oauth2.googleapis.com/token`
     using `GMAIL_OAUTH_CLIENT_ID` / `GMAIL_OAUTH_CLIENT_SECRET` /
     `GMAIL_REFRESH_TOKEN`. The access token is cached in memory and reused until
     ~60s before expiry.
   - Send via `POST .../upload/gmail/v1/users/me/messages/send?uploadType=media`
     with `Content-Type: message/rfc822` and the **raw MIME bytes** as the body.
     The raw-upload variant avoids base64url `{raw}` encoding/bookkeeping.
   - The MIME is generated by **nodemailer** in `streamTransport` mode (build, do not
     send). This reuses nodemailer's proven RFC2047 encoded-word handling — Thai
     subjects (e.g. `ยืนยันอีเมลของคุณ`) are encoded correctly — and its
     `multipart/alternative` (text + html) assembly.
   - Both fetches are bounded by a ~10s `AbortController` timeout. Failures return/
     throw with the HTTP status; **tokens are never logged** (the token-request body
     is never logged; only Gmail's error JSON, which does not echo the bearer token).

2. **MailService integration** (`mail.service.ts`):
   - If `GMAIL_REFRESH_TOKEN` + a client id/secret are configured → Gmail API is the
     PRIMARY path; otherwise SMTP (unchanged behaviour). Client id/secret fall back
     to the existing `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` so the owner can
     reuse one OAuth client and add only `GMAIL_REFRESH_TOKEN`.
   - Retry/backoff, `Promise<boolean>` results, and the dev `[MAIL-FALLBACK]` link
     logging are preserved and shared across both transports.
   - `isTransientMailError` is extended for HTTP semantics: **429 + 5xx are
     transient** (retry), **400/401/403 are permanent** (a revoked token or bad
     scope fails identically every time). Note this is the INVERSE of SMTP
     response-code semantics, so HTTP errors carry a distinct `httpStatus` field
     rather than reusing nodemailer's `responseCode`.
   - **Boot probe stays non-blocking.** In Gmail mode the probe refreshes the access
     token fire-and-forget (`void this.verifyGmail()`), exactly like the SMTP
     `verifyTransport()`. Boot must NEVER await network I/O — awaiting it is the
     exact bug that previously 502'd Railway (the process loads but never binds the
     port). This contract is pinned by a test.

3. **One-time consent helper** `ops/scripts/gmail-oauth-setup.mjs` (plain Node, no
   deps): reads the OAuth client id/secret from `apps/api/.env` (or env/argv), starts
   a localhost:8765 server, prints the consent URL (scope `gmail.send`,
   `access_type=offline`, `prompt=consent`), captures the redirect code, exchanges it,
   and prints the refresh token + the exact env lines to paste.

## DMARC / sender alignment

`EMAIL_FROM` **must remain the Gmail account** that authorised the refresh token.
Gmail signs outgoing mail (DKIM) for that account; a `From:` on any other domain
would fail DMARC alignment and land in spam or bounce. This is unchanged from the
SMTP setup — only the transport differs.

## Alternatives considered

- **Third-party ESP (SendGrid/Postmark/Resend):** rejected — owner wants no ESP; mail
  stays self-owned on the existing Gmail account.
- **A different PaaS / paid Railway tier that allows SMTP:** out of scope for this
  change and doesn't remove the dependency on an open SMTP egress path.
- **Gmail API JSON `{raw}` variant (base64url):** works, but the media-upload
  `message/rfc822` variant is simpler (hand Gmail the bytes verbatim, no encoding
  step to get wrong).

## Consequences

- **Positive:** email delivers in production over HTTPS regardless of SMTP egress
  policy; no new runtime dependency (Node 20 native `fetch` + existing nodemailer);
  sender identity and DMARC alignment unchanged; SMTP path (Mailpit) still works for
  local dev untouched.
- **Neutral:** one more set of env vars and a one-time OAuth consent step. The Gmail
  API free quota (~1e9 quota units/day; a send costs ~100) is far above this app's
  transactional volume.
- **Watch:** a refresh token can be revoked (password change, "remove access", 6
  months unused while the OAuth app is in Testing mode). When that happens the boot
  probe logs `Gmail API verify FAILED` and sends return `false`; the fix is to re-run
  the setup script and update `GMAIL_REFRESH_TOKEN`. Consider publishing the OAuth
  consent screen (Production) to avoid the 6-month Testing-mode refresh-token expiry.
